# 创想集为什么选择 Monad：实现与证据边界

## 场景与取舍

创想集服务于“逛一次作品展，支持多个好想法”。作品可以是项目、Ideas、工具或资料。目录公开可读；支持者选择多个作品，使用一个有界批量交易直接向作者付款。平台不托管支持资产，也不抽取支持手续费，用户仍支付链上 Gas。

链上存储与执行的价值在于规则可独立核验：内容绑定发布地址，收藏与支持公开记录，作者归档权限与原子转账由合约约束。它不自动赋予版权、身份真实性或抗刷声誉。Web2 方案更便宜、更容易删改和治理；公开、难以删除以及 Gas 成本是我们明确承担的代价。

## 已落地的适配

使用标准 Solidity、OpenZeppelin 和 ethers，复用 EVM 工具链。Monad 并行执行保持顺序 EVM 语义，兼容性不要求应用发明专有合约。我们的 batch 是一笔交易内部的顺序执行，不能据此声称获得并行加速；totalSupport 与作者统计仍是共享状态，没有并发收益实测。

Monad 按 gas_limit 计费。前端先 estimateGas，再加 10% 余量，而不是随意给出巨大上限；发布前展示正文字节数、费用估算与费用上限。按当前有效费率估算时，费用为 gas_limit × gas_price；实际费率变化和用户修改钱包参数会改变结果。

正文限制 6,000 UTF-8 字节，大附件使用外部公开链接。支持篮上界 20，是当前保守的有界执行设计，不是链级限制或已证明的最优参数。用户可分批支持更多作品，但多批之间不具有整体原子性。

## 已取得的真实网络证据

`deployment/testnet-audit.json` 记录了 Monad 测试网 10143 的 RPC 核验、已部署代码与历史源码匹配、币种精度及平台币关联。两个旧版合约已在 Monadscan 与 Monadvision 验证成功，原始结果在 `verification/`。该平台版本支持单笔支持，没有 supportBatch。

在核验快照、当时 102 MON-gwei 费率下，100/1,000/6,000 字节正文含 10% Gas 余量的 RPC 估算分别约为 0.02682906、0.082885098、0.396391584 MON。原始输入与结果见 `scripts/audit-testnet.mjs` 和 `benchmarks/monad-estimates.json`。这不是实付费用，不包含法币换算，也不能证明比其他链便宜。

本地同起点、三位不同作者的三项支持测得 380,145 对 299,020 Gas，每项从 126,715 降至 99,673 Gas，约减少 21.34%。它用于验证批处理在这个 EVM 场景的固定开销收益，不能迁移成 Monad 的批量节省比例、确认时间或吞吐结果。

### Monad RPC 上的新版字节码模拟

除了本地链，`npm run testnet:simulate -- --account 0x公开地址` 会把当前 `CreationHub` 的完整运行时代码放到 Monad 测试网的只读 state override 中，并合成测试币余额、授权和作品行，再用 `eth_estimateGas` 比较单笔与批量。结果记录在 `benchmarks/monad-batch-simulation.json`：

- 三位不同作者的三笔单笔合计 527,145 Gas；一笔三项批量 354,571 Gas，估算减少 172,574 Gas（32.74%）。
- 20 项上限的批量估算为 1,792,860 Gas，含 10% 余量约 1,972,146 Gas；在当前 102 MON-gwei 费率下约 0.201158892 MON。
- 新版 hub 部署代码估算 1,558,541 Gas；发布 100/1,000/6,000 字节正文分别估算 285,019 / 784,627 / 3,578,803 Gas。

这不是“已部署新版合约”的证据：模拟地址没有代码，余额和作品是 state override，估算也不是交易回执。它证明的是新版字节码可以在 Monad RPC 上执行，并给出部署前的成本上界。真实部署、源码验证、真实 `supportBatch` 回执仍必须补齐。

## 补齐成交证据的方法

使用网页钱包签署真实发布、支持交易后，将完整 hash 交给只读取证脚本：

```sh
npm run capture:testnet -- 0x完整交易哈希
```

脚本检查链 ID、目标 hub、成功状态、规范区块与 finalized 高度、调用方法及对应事件。成功后生成 `benchmarks/monad-transactions.json`；发布和支持都具备时生成当前 hub 的回执验收结果。它不会签名，不索取私钥，不把未知的提交等待时间作为确认性能记录。

回执验收仍不能替代浏览器验收、多钱包体验、不同作者场景或用户反馈。新版批量 hub 尚需一笔钱包部署交易；原有 BLITZ 可复用，但旧目录、收藏和授权不会自动迁移。

## 并行执行与状态竞争的边界

Monad 的并行执行对合约保持顺序 EVM 语义，应用不需要为了兼容改写状态机。支持篮在一个交易里顺序遍历最多 20 个作品，`totalSupport`、`received[author]` 和每个 `Creation.support` 都是共享状态：同一作者或同一全局计数器上的并发交易会竞争，不能声称这批操作已经获得并行加速。

当前设计把作品行按 `id` 分散存储，不同作品的支持写入落在不同 slot；但 `totalSupport` 仍是全局热点，作者累计收入也按作者地址集中。若未来要针对并行执行优化，可先把全局总数改为事件派生或分片计数器，再按作者/作品拆分统计；这些改动需要同时证明读取一致性、索引成本和并发收益。现在没有公共压力数据，因此不提前引入复杂状态布局，也不把“多个 slot”当成并行性能证明。

## 与其他 EVM 链的关系

这个产品并非只能运行在 Monad：标准 Solidity、OpenZeppelin 和 ethers 可以在任何 EVM 链上部署。选择 Monad 的实际理由是低固定交易成本、较快确认和 EVM 兼容性，让“小额、多作者、可原子回滚”的支持篮更容易被普通用户接受；而不是宣称其他链无法实现同样的接口。

如果评委会追问“为什么不是任意 EVM 链”，诚实回答应包含三点：第一，当前没有做跨链费用对照，不能声称 Monad 一定更便宜；第二，代码没有使用 Monad 专有 API，迁移成本低，这既是兼容性优势，也是差异化不足；第三，下一步要用同一笔批量交易在 Monad 上取得真实回执，并与至少一条对照链的同状态估算比较。没有这组数据前，产品定位是“为 Monad 的低成本高频交互设计”，不是“只有 Monad 能做”。

## 当前最值得完成的三步

1. 用已有测试币部署新版 hub，核验与验证新地址，并更新公共配置；这是当前唯一阻挡公共批量演示的链上步骤。
2. 完成真实发布和不同作者的 `supportBatch`，导入完整交易 hash，重新截图并明确网络；模拟估算不能替代这一步。
3. 邀请实际创作者和支持者试用，记录困惑、任务结果和失败原因；未收集前不宣称用户需求已验证。
